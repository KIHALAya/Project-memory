[SECTION] 2.1 GPU Computing Foundations

GPUs have evolved from specialized graphics accelerators into the dominant computational paradigm for modern artificial intelligence, enabling the training of deep neural networks and large-scale AI workloads that would be infeasible on traditional CPU architectures. This section establishes the theoretical and architectural foundations of GPU computing, with particular emphasis on NVIDIA's CUDA platform as the industry-standard framework for parallel computing.

The transition from graphics-specific hardware to general-purpose parallel processors began in the early 2000s, culminating in NVIDIA's 2006 introduction of CUDA, which decoupled GPU computing from graphics APIs and enabled direct programmability for computational workloads. Since then, GPU computing has accelerated applications ranging from scientific simulations (fluid dynamics, energy transport) to business analytics and, most significantly, deep learning algorithms including image classification, diffusion models, and large language models.

GPUs provide substantially higher instruction throughput and memory bandwidth than CPUs within comparable price and power envelopes. Where a CPU is optimized for executing serial thread sequences with low latency (handling a few tens of threads in parallel), a GPU excels at executing thousands of threads concurrently, trading single-thread performance for aggregate throughput. This architectural distinction makes GPUs indispensable for AI workloads characterized by massive matrix operations and data-parallel computations.

Key architectural characteristics distinguishing GPUs from CPUs:
Feature	CPU	GPU
Design Philosophy	Latency-oriented: complete individual tasks quickly	Throughput-oriented: process large data volumes in parallel 
Core Count	Small (typically 4–64 cores)	Massive (hundreds to thousands of cores) 
Transistor Allocation	More transistors for data caching & flow control	More transistors for data processing units

Cache Size	Large L1/L2/L3 caches	Smaller caches, compensated by high memory bandwidth 
Control Logic	Complex: branch prediction, out-of-order execution	Simplified: optimized for repetitive parallel operations 
Memory Bandwidth	Moderate (50–100 GB/s)	Very high (200–1,500 GB/s) 
Parallelism Model	Limited thread parallelism	Massive thread parallelism (10,000+ concurrent threads)

[SUBSECTION] 2.1.1 CUDA Architecture Overview

CUDA (Compute Unified Device Architecture) is NVIDIA's parallel computing platform and programming model that enables general-purpose computing on GPUs. Introduced in 2006 with the GeForce 8-series, CUDA represented a paradigm shift by providing a C-like programming interface that exposed GPU parallelism independently from graphics APIs. Before CUDA, GPU computing required embedding computational kernels within graphics pipeline code (vertex/fragment shaders); CUDA unified the shader architecture into programmable "CUDA cores" and enabled direct computational programming.

Historical Context and NVIDIA's Contribution:

The development of CUDA originated from Stanford University's Brook GPU project, led by Ian Buck, which pioneered stream programming on GPUs. NVIDIA acquired this technology and spent two years developing CUDA 1.0, which shipped in 2006. This represented NVIDIA's strategic commitment to transforming GPUs from specialized graphics processors into general-purpose parallel computing accelerators. Since 2006, NVIDIA has continuously enhanced CUDA with new features, architectural improvements, and ecosystem expansion, establishing it as the de facto standard for GPU computing with millions of developers worldwide.

Internal GPU Organization:

At the hardware level, an NVIDIA GPU consists of an array of Streaming Multiprocessors (SMs), on-chip L2 cache, and high-bandwidth DRAM. Each SM is a fundamental execution unit containing multiple streaming processors (CUDA cores), warp schedulers, register files, shared memory, and specialized execution units including Tensor Cores for AI acceleration.

For example, the NVIDIA A100 GPU (Ampere architecture) contains 108 SMs with 64 CUDA cores per SM, totaling 6,912 cores capable of 221,184-way parallelism (32 threads per warp). Each SM can manage up to 64 warps (2,048 threads) simultaneously, processing 4 warps at a time through its warp schedulers.

Streaming Multiprocessors (SMs):

The Streaming Multiprocessor is the core execution unit of NVIDIA GPUs. Each SM contains:

CUDA Cores (Stream Processors): Individual processing units that execute floating-point and integer operations. These are SIMT (Single Instruction Multiple Threads) cores where groups of 32 cores execute the same instruction simultaneously on different data.

Warp Schedulers: Each SM contains multiple warp schedulers (typically 4 in modern architectures) that select warps for execution. Each scheduler manages its own queue of warps and selects eligible warps based on operand availability.

Register File: A SUPER LARGE register file per SM (typically 64K–256K registers depending on architecture) enables zero-overhead context switching by keeping thread state in registers.

Shared Memory/L1 Cache: Program-configurable memory (typically 48–96 KB per SM) that can be partitioned between shared memory (for thread-block communication) and L1 cache. This memory has extremely low latency (few cycles) and very high bandwidth (>1 TB/s aggregate).

Execution Units:

CUDA Cores: For general FP32/INT32 operations

Tensor Cores: Introduced in Volta architecture (2017) specifically for matrix multiply-accumulate operations crucial to deep learning. Tensor Cores operate on small matrix blocks (e.g., 4×4) and can compute/accumulate in higher precision than inputs (e.g., FP16 inputs with FP32 accumulation).

SFUs (Special Function Units): For transcendental functions (sin, cos, exp, log)

LD/ST Units: Load/store units for memory operations

Caches: L1 data cache and texture cache for memory access optimization.

Warp Execution and SIMT Model:

A warp consists of 32 consecutive threads within a thread block that execute the same instruction simultaneously. This execution model is termed SIMT (Single Instruction Multiple Thread), which is conceptually similar to SIMD (Single Instruction Multiple Data) vectorization on Intel CPUs but operates at the thread level.

Key characteristics of warp execution:

Lock-step Execution: All 32 threads in a warp execute the same instruction at the same time, each operating on different data

Warp Formation: Threads are serialized into warps based on thread ID (threads 0–31 form warp 0, threads 32–63 form warp 1, etc.)

Warp Size: Fixed at 32 threads for all CUDA compute capabilities

Branch Divergence: When threads within a warp take different execution paths (e.g., due to conditional branches), the warp serializes execution of each path, reducing efficiency. Full efficiency is realized when all 32 threads agree on their execution path.

Zero-Overhead Scheduling: SMs implement zero-overhead warp scheduling where warps whose next instruction has operands ready are eligible for execution, selected based on prioritized scheduling policy

Parallel Computing Principles:

CUDA exposes multiple levels of parallelism to programmers:

Data Parallelism: The same operation applied to different data elements simultaneously. Each thread processes a subset of the data.

Thread-Level Parallelism: Thousands of threads execute concurrently across multiple SMs.

Instruction-Level Parallelism: Within each warp, multiple instructions can be in pipeline simultaneously due to heavy pipelining.

The GPU architecture progresses differently from CPU architecture: while CPUs focus on increasing clock speed and complex control logic (branch prediction, out-of-order execution), GPUs increase core count, memory bandwidth, and throughput. GPUs divide processor resources spatially across stages rather than temporally through pipelining, with each stage feeding directly into the next.

Hardware Acceleration Concepts:

GPU acceleration leverages the throughput capability of GPUs to accelerate computational workloads. Key principles include:

Massive Parallelism: GPUs execute thousands of threads concurrently, enabling 10,000+ way parallelism

High Memory Bandwidth: Modern GPUs achieve 200–1,500 GB/s memory bandwidth compared to 50–100 GB/s for CPUs

Specialized Hardware: Tensor Cores provide dedicated acceleration for matrix operations critical to AI, achieving orders-of-magnitude speedup over general-purpose cores

Energy Efficiency: GPUs deliver higher FLOPS per watt than CPUs for parallel workloads, with lower computational cost per GFLOPS

Real-World Examples:

A100 GPU: 108 SMs, 6,912 CUDA cores, 221,184-way parallelism, 1,500 GB/s memory bandwidth

H100 GPU (Hopper): Enhanced SM architecture with improved Tensor Cores for FP8 precision, supporting transformer engine for LLM training

Blackwell Ultra: Latest architecture with refined SM design, increased Tensor Core density, and improved memory hierarchy for AI factory workloads

[NOTE]
Engineering Consideration: The fixed warp size of 32 threads and lock-step execution impose important constraints on algorithm design. Kernel developers must ensure thread blocks are multiples of 32 for optimal occupancy, and minimize branch divergence within warps to maintain execution efficiency. Poorly designed kernels with significant divergence can suffer 50%+ performance degradation compared to divergence-free equivalents.

[/NOTE]

Limitations and Challenges:

Despite their advantages, GPU computing presents several challenges:

Programming Complexity: CUDA requires explicit management of thread hierarchies, memory transfers, and synchronization, increasing development complexity compared to CPU programming

Vendor Lock-in: CUDA is proprietary to NVIDIA, creating ecosystem dependency. While alternatives exist (OpenCL, ROCm), CUDA's maturity and library ecosystem maintain its dominance

Memory Constraints: GPU memory (typically 8–80 GB) is limited compared to CPU memory, constraining problem sizes for large models

Latency Sensitivity: GPUs excel at throughput but have high memory latency (400–800 cycles for global memory), requiring massive parallelism to hide latency

Branch Divergence: Conditional branching within warps serializes execution, reducing parallel efficiency

[SUBSECTION] 2.1.2 CUDA Execution Model

The CUDA execution model defines how parallel computations are organized, scheduled, and executed on GPU hardware. Understanding this model is essential for writing efficient CUDA kernels and optimizing AI workloads.

Thread Hierarchy:

CUDA organizes threads into a two-level hierarchy consisting of thread blocks and grids:

Threads: The smallest execution unit. Each thread executes the same kernel code (SPMD—Single Program Multiple Data) but operates on different data based on its unique thread index.

Thread Blocks: Groups of threads that can:

Share data through shared memory

Synchronize execution using barriers

Cooperate on computations

All threads in a block execute the same kernel program, with each thread/warp handling a small portion of the task. Block sizes are typically multiples of 32 (warp size) for optimal occupancy, commonly 128, 256, 512, or 1024 threads per block.

Grids: The collection of all thread blocks executing a kernel. The grid encompasses the entire parallel computation.

SIMT Execution Model:

CUDA implements SIMT (Single Instruction Multiple Thread) execution, where:

All threads in a warp execute the same instruction simultaneously

Threads within a warp execute synchronously in lock-step fashion

Warps within a block execute asynchronously and may proceed in any order relative to one another

Different warps execute independently regardless of whether they execute common or disjoint code paths

This model differs from traditional SIMD by providing individual thread program counters and stack space, enabling more flexible parallel programming while maintaining SIMD-like efficiency for aligned workloads.

Warp Scheduling:

Each SM contains multiple warp schedulers (typically 4) that manage warp execution:

Each scheduler maintains its own queue of warps

Warps are assigned to schedulers for their lifetime

Eligible warps (those with operands ready for consumption) are selected based on prioritized scheduling policy

Zero-overhead scheduling ensures no empty slots while pending instructions exist

Each SM can manage 64 warps (2,048 threads) but processes only 4 warps simultaneously

Synchronization Mechanisms:

CUDA provides several synchronization primitives:

Thread Block Synchronization: __syncthreads() barrier ensures all threads in a block reach the point before any proceeds

Grid-Level Synchronization: Requires multiple kernel launches; cannot synchronize across blocks within a single kernel

Warp-Level Primitives: __syncwarp() for warp-level synchronization (compute capability 7.0+)

Kernel Execution Lifecycle:

Host Launch: CPU initiates kernel execution with execution configuration specifying grid and block dimensions

Block Assignment: Runtime assigns thread blocks to available SMs. Blocks can execute in any order relative to each other

Warp Formation: SM divides blocks into warps (32 threads each)

Instruction Issuing: Warp schedulers issue instructions to execution units at warp level

Execution: Threads execute in lock-step within warps across SMs

Completion: Kernel completes when all threads in all blocks finish execution

Massive Parallel Execution Organization:

CUDA organizes massive parallelism through:

Transparent Scaling: Hardware automatically schedules blocks across available SMs, enabling code to scale across different GPU configurations

Occupancy Optimization: Maximizing active warps per SM (up to 64 warps/2,048 threads) improves latency hiding through thread-level parallelism

Independent Block Execution: Blocks execute independently, enabling flexible scheduling and load balancing

[NOTE]
Engineering Optimization: Optimal kernel performance requires careful configuration of block size (typically 128–512 threads), ensuring block sizes are multiples of 32 for warp alignment, and maximizing occupancy while respecting register and shared memory constraints per SM. Poor occupancy can reduce effective throughput by 30–50% compared to optimized configurations.

[/NOTE]

[SUBSECTION] 2.1.3 CUDA Kernels and Programming Model

CUDA kernels are functions that execute on the GPU (device) and are invoked from the CPU (host). They form the fundamental unit of parallel computation in CUDA programming.

CUDA Kernels:

A kernel is a function declared with the __global__ qualifier that executes on the device in parallel across multiple threads:

cpp
__global__ void kernel_name(parameters) {
    // Parallel code executed by all threads
}
All threads execute the same kernel code (SPMD model), with each thread computing its unique index to determine which data subset to process.

Host-Device Interaction:

CUDA programs consist of:

Host Code: Serial or modestly parallel code running on CPU, responsible for:

Memory allocation on device (cudaMalloc)

Data transfer from host to device (cudaMemcpy)

Kernel launch with execution configuration

Data transfer from device to host

Memory deallocation (cudaFree)

Device Code: Highly parallel kernel code running on GPU, executing the data-parallel portion of the application

Kernel Launches:

A kernel must be called with an execution configuration specifying grid and block dimensions:

cpp
kernel_name<<<gridDim, blockDim>>>(parameters);
Where:

gridDim: Grid dimensions (number of blocks)

blockDim: Block dimensions (threads per block)

The execution configuration is placed between the function name and parameters using triple-angle-bracket syntax.

Thread Indexing:

Each thread computes its unique global index using built-in variables:

threadIdx.x/y/z: Thread index within block

blockIdx.x/y/z: Block index within grid

blockDim.x/y/z: Block dimensions

Parallel Decomposition:

Efficient CUDA programs decompose problems into parallel units:

Data Decomposition: Each thread processes one or more data elements (e.g., one array element per thread)

Domain Decomposition: For multi-dimensional data (images, matrices), threads are organized in 2D or 3D blocks matching data structure

Grid-Stride Loop: Pattern where threads process multiple elements using stride equal to total grid size, enabling flexible problem sizes:

cpp
int stride = blockDim.x * gridDim.x;
for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
    // Process element i
}
Kernel Optimization Strategies:

Memory Coalescing: Align memory accesses so consecutive threads access consecutive memory addresses, maximizing memory throughput

Shared Memory Usage: Cache frequently accessed data in shared memory to reduce global memory latency (20–30 cycles vs. 400–800 cycles)

Occupancy Maximization: Balance register and shared memory usage to maximize active warps per SM

Minimize Branch Divergence: Structure code to minimize conditional branches within warps

Use Vendor Libraries: Leveraging optimized libraries (cuBLAS, cuDNN) provides better performance than custom implementations

Importance in AI Frameworks:

CUDA kernels form the foundation of modern AI frameworks:

PyTorch: Uses CUDA for tensor operations, with autograd engine leveraging CUDA kernels for forward/backward passes. PyTorch tensors backed by CUDA memory execute operations through CUDA kernels

TensorFlow: Similarly relies on CUDA for GPU-accelerated operations, with TF-TRT (TensorFlow TensorRT) integration for further optimization

Underlying Libraries: Both frameworks primarily accelerate through NVIDIA libraries:

cuBLAS: Basic Linear Algebra Subprograms for matrix operations

cuDNN: Deep Neural Network library for convolution, pooling, normalization, and RNN operations

NCCL: NVIDIA Collective Communications Library for multi-GPU communication

These frameworks achieve GPU acceleration by calling optimized CUDA kernels from these libraries rather than implementing custom kernels, providing productivity, performance, and portability.

Registers:

Registers are the fastest memory available to each thread, with approximately 1-cycle latency and ~8 TB/s bandwidth. Each SM has a large register file (32K registers unified per SM), with up to ~21 registers per thread depending on kernel complexity. Registers are used for:

Local variables

Thread indices

Intermediate computation results

Excessive register usage can limit occupancy (number of concurrent warps per SM), creating a tradeoff between register pressure and parallelism.

Shared Memory:

Shared memory is program-configurable SRAM accessible by all threads in a block, typically 48–96 KB per SM depending on architecture. Key characteristics:

Capacity: Up to 48 KB (Volta) to 96 KB (Ampere+) per SM

Latency: 20–30 cycles (significantly lower than global memory's 400–800 cycles)

Bandwidth: >1 TB/s aggregate

Usage Pattern: Store frequently accessed data, tile matrices for GEMM operations, enable inter-thread communication within blocks

Partitioning: Can be configured as 16 KB shared + 48 KB L1 or 48 KB shared + 16 KB L1 (or variants depending on architecture)

Shared memory is critical for AI workload optimization, particularly for:

Tiled matrix multiplication (reducing global memory accesses)

Convolution operations (sharing input activations across threads)

Reduction operations (partial results in shared memory)

Global Memory:

Global memory (GPU DRAM) is the main means of communicating data between host and device, visible to all GPU threads:

Capacity: 8–80 GB depending on GPU model (e.g., A100 has 40/80 GB, H100 has 80 GB)

Latency: 400–800 cycles (high latency)

Throughput: ~200 GB/s (entry-level) to ~1,500 GB/s (high-end A100/H100)

Access Pattern: All accesses go through L2 cache, including copies to/from CPU host

Constant Memory:

Constant memory is read-only (64 KB) with specialized caching optimized for broadcast access patterns:

Usage: Store kernel constants accessed uniformly by all threads

Bandwidth: ~800 GB/s when all threads in warp access same address (broadcast)

Optimization: Best when threads in warp access same constant address

Local Memory:

Local memory is used when registers are exhausted and variables spill to global memory. It has similar latency and bandwidth to global memory and should be avoided in performance-critical kernels.

Cache Hierarchy:

Modern NVIDIA GPUs implement a multi-level cache hierarchy:

L1 Cache/Shared Memory: Per-SM, configurable partitioning

L2 Cache: Per-GPU, shared across all SMs, few MB capacity

Texture Cache: Optimized for 2D spatial locality, ~800 GB/s

All global memory accesses pass through L2 cache, which provides a unified caching layer across the GPU.

Memory Coalescing:

Memory coalescing is critical for achieving high global memory throughput. Coalesced access occurs when consecutive threads in a warp access consecutive memory addresses, allowing the hardware to combine multiple accesses into fewer transactions.

Coalesced access pattern:

cpp
// Good: consecutive threads access consecutive addresses
float value = global_array[threadIdx.x];
Uncoalesced access pattern:

cpp
// Poor: strided access reduces throughput
float value = global_array[threadIdx.x * stride];
Uncoalesced access can reduce memory throughput by 10–50× compared to coalesced access.

Memory Latency and Hiding:

Due to high global memory latency (400–800 cycles), GPUs rely on massive thread-level parallelism to hide latency. When a warp waits for memory, the warp scheduler switches to another ready warp, achieving zero-wait execution if occupancy is sufficient.

Key principles:

Latency Hiding: Maintain high occupancy (many active warps) so scheduler always has ready warps when others wait for memory

Memory Throughput: Optimize for bandwidth utilization rather than latency reduction

Bank Conflicts: Shared memory has 32 memory banks; bank conflicts occur when threads in warp access same bank, serializing access

Performance Implications:

Memory-Bound vs Compute-Bound: Kernels are memory-bound when performance limited by memory bandwidth, compute-bound when limited by FLOPS. AI workloads (matmul, convolutions) are often memory-bound without optimization

AI Workload Optimization:

Use shared memory tiling for matrix operations

Ensure coalesced global memory access

Minimize register pressure to maintain occupancy

Leverage Tensor Cores for matrix operations (reduces memory traffic via higher computation density)

Bottlenecks:

Global Memory Bandwidth: Primary bottleneck for memory-bound kernels

Shared Memory Bank Conflicts: Can reduce shared memory throughput significantly

Register Pressure: Excessive registers reduce occupancy, limiting latency hiding

Uncoalesced Access: Dramatically reduces effective bandwidth

Systolic Array Architecture:

Partial Sums	Accumulate as data moves down columns 
Result	Entire matrix multiplication completes as data flows through array 
Key Advantage: Each data element is read once from memory and reused across many computations as it flows through the array, dramatically reducing memory bandwidth requirements.

[SUBSECTION] 2.2.2 AI Accelerator Design Principles

AI accelerator design follows domain-specific architecture (DSA) principles that optimize hardware exclusively for neural network computation, abandoning general-purpose capabilities to maximize tensor operation efficiency.

Domain-Specific Architecture (DSA):

DSA philosophy abandons generality to achieve orders-of-magnitude improvement in performance and energy efficiency for specific workloads:

Specialization: Hardware designed exclusively for neural network operations (matrix multiply, convolution, activation functions)

Silicon Allocation: Transistors allocated to compute units and on-chip memory rather than control logic or caching

Elimination of Overhead: Removal of graphics pipelines, branch prediction, out-of-order execution, and cache coherence not utilized for AI

ASIC-Based Design Philosophy:

AI accelerators use ASIC (Application-Specific Integrated Circuit) design:

Characteristic	Description
Fixed Functionality	Hardware optimized for specific operations (MatMul, Conv, Attention) 
Non-Reconfigurable	Unlike FPGAs, circuit is fixed at fabrication 
Optimal Performance	Achieves highest performance-per-watt for target workload 
High NRE Cost	Non-recurring engineering costs for design and fabrication

Parallel Execution Scheduling at Chip Level:

NPU schedulers parallelize execution across hardware:

Layer-Level Parallelism: Different layers scheduled on different cores (Ascend 910 has 32 cores)

Intra-Layer Parallelism: Single layer split across MAC array (e.g., 4,096 MACs per core)

Pipeline Parallelism: Stages of computation (load, compute, activate, store) overlapped in time

Compute Pipeline Optimization for Throughput:

Double Buffering: While one tile is being computed, next tile is being loaded from memory

Zero-Skipping: Dispatching Unit bypasses MAC operations for zero-valued weights/activations

Data Reuse: Weights/activations reused across computations without memory reload

[SUBSECTION] 2.2.4 NPU Memory and Dataflow Architecture

NPU memory system design prioritizes minimizing data movement, which dominates AI computation cost due to the ~200–1,000× higher energy cost of off-chip memory access compared to PE register access.

On-Chip SRAM:

On-chip SRAM serves as the primary buffer between off-chip memory and compute units:

SRAM Type	Capacity	Function	Access Cost
Global Buffer	16–24 MB (e.g., TPU v1)	Prefetches tiles from DRAM 
~20× register 
PE Local SRAM	KB per PE	Local data for MAC units 
~2× register 
Register File	Bytes per PE	Immediate MAC operands 
1× (baseline) 
Buffer Hierarchies:

NPU memory hierarchy uses tiling and double buffering strategies:

Tiling: Large tensors split into tiles that fit in on-chip SRAM

Double Buffering: Overlap data transfer (DMA) with computation

Prefetching: Next tile loaded while current tile is computed

Memory Bandwidth Constraints:

Memory bandwidth is the primary bottleneck in AI computation:

Memory Type	Bandwidth	Latency	Use Case
HBM2	1,228 GB/s (Ascend 910)	100+ cycles	Large models, training 
DDR4	25–50 GB/s	200+ cycles	Edge inference
On-Chip SRAM	>1 TB/s	1–5 cycles	Active weights/activations 
Huawei Ascend 910 connects to four HBM2 channels delivering 1,228 GB/s to 32 GB memory, enabling efficient operation on large models.

Data Reuse Strategies:

NPUs maximize data reuse through dataflow strategies:

Strategy	Data Reused	Reuse Factor	Benefit
Weight-Stationary	Weights in PE	1,000–10,000×	Minimal weight reloads 
Output-Stationary	Partial sums in PE	100–1,000×	Reduced write-back 
Input-Stationary	Inputs in PE	100–1,000×	Specific layer optimization 
Row-Stationary	Weights + PSUMs	100–10,000×	Balanced reuse 
Weight/Activation Streaming:

Data streaming patterns minimize memory transfers:

Weights: Loaded once, streamed across all inputs (inference)

Activations: Streamed through systolic array, partial sums accumulated

Synchronization: Data loading parallel to computation (input from West, weights from North)

Compute-Memory Decoupling:

NPU architecture decouples computation from memory:

DMA Engines: Handle data transfers independently of compute

Asynchronous Execution: Compute and memory operations overlap

Non-Blocking Loads: Memory continues loading while compute executes

Dataflow Execution Models:

Dataflow	PE State	Data Flow	Optimized For
Weight-Stationary (WS)	Weights fixed	Inputs flow West→East, Outputs flow South	Inference, large batches 
Output-Stationary (OS)	PSUMs fixed	Inputs/Weights flow, PSUMs accumulate	Reducing write-back
Row-Stationary (RS)	Weights+PSUMs fixed	Optimized reuse	Eyeriss, balanced workloads

API Category	Function

Scheduling System:

[SUBSECTION] 2.3.6 Performance and Execution Model Characteristics

Ascend NPUs exhibit specific performance characteristics in throughput, latency, scaling efficiency, and operator-level acceleration that distinguish them from GPU execution models.

Throughput vs Latency Trade-offs:

Workload Type	Configuration	Throughput	Latency
Inference (Small Batch)	Batch=1	Lower	Minimal (1–3 ms)
Inference (Large Batch)	Batch=128–512	Maximum (300–600 img/s)	Higher (10–50 ms)
Training	Batch=512–2048	Maximum (1,802 img/s ResNet-50)	Not applicable (throughput-optimized) 
Ascend 910 + MindSpore achieves 1,802 images/second for ResNet-50 V1.5 on ImageNet 2012, 2× mainstream GPU + TensorFlow (965 img/s).

Distributed Scaling Efficiency:

Scale	Configuration	Efficiency	Notes
Single Node	8× Ascend 910	~95%	HCCS interconnect 
Small Cluster	128 nodes	~90%	100G RoCE 
Large Cluster	1,024–2,048 nodes	~85%	512 PFLOPS total 
Memory Bandwidth Optimization:

Optimization Technique	Effect
Explicit Memory Hierarchy	MTE manages L0/L1/SRAM transfers 
Tiling	Large tensors split to fit SRAM
Double Buffering	Overlap DMA with computation
Cross-Layer Memory Reuse	30–50% memory footprint reduction 
Ascend 910 achieves 1,228 GB/s off-die bandwidth via 4× HBM2 channels, comparable to NVIDIA A100 (1,555 GB/s).

Operator-Level Acceleration:

Operator	Hardware Acceleration	Performance
Conv2D	Cube unit (4096 FP16 MACs)	256 TFLOPS/s peak 
MatMul	Cube unit	256 TFLOPS/s peak 
Activation (ReLU)	Vector unit	2,048-bit parallel 
Video Decode	DVPP (128 channels)	H.264/265 @ FHD 
Cluster-Level Parallelism:

Parallelism Type	Mechanism	Scale
Data Parallel	Gradient aggregation via HCCL	1,024–2,048 nodes 
Model Parallel	Layer splitting across nodes	Large models (>100B params)
Pipeline Parallel	Stage execution overlap	Transformer models
